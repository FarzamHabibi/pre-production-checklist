# Hosting

[← back to repository](../README.md)

The site is a folder of static files generated by `scripts/build_site.py`. Anything that
serves static files will do. Two are set up.

## GitHub Pages — currently live

Built and deployed by [`.github/workflows/site.yml`](../.github/workflows/site.yml) on
every push to `main`. Nothing is committed; the workflow builds and uploads an artifact.

Live at https://farzamhabibi.github.io/pre-production-checklist/

## Cloudflare Pages — for a shorter domain

Cloudflare Pages gives a free `*.pages.dev` hostname immediately, and unlike GitHub
Pages it serves the response headers in `_headers`.

```bash
npx wrangler login                    # once, opens a browser
./scripts/deploy-cloudflare.sh        # builds and deploys
```

The first deploy creates the project and prints the URL. It is a **direct upload** — the
repository is not connected to Cloudflare and no API token is stored anywhere, which is
the least-privilege option and the one to prefer while you are the only person deploying.

The script refuses to upload a build whose canonical URL does not match the host it is
being deployed to, because a canonical pointing somewhere else is worse than none.

### If the project name is taken

```bash
PRODCHECK_CF_PROJECT=prodcheck-dev ./scripts/deploy-cloudflare.sh
```

### Adding a real domain later

Buy it, add it in the Cloudflare Pages project under **Custom domains**, then:

```bash
PRODCHECK_SITE=https://prodcheck.dev ./scripts/deploy-cloudflare.sh
```

## Running both at once

That is fine and is what happens today, but only one host may be canonical or search
engines see duplicate content. The build stamps `SITE` into every canonical tag, `og:url`
and sitemap entry, so whichever URL you build with is the canonical one — and the other
host serves pages that point at it.

To make Cloudflare canonical, set the environment variable in the GitHub Pages workflow
too, so both builds agree:

```yaml
      - name: Build the site
        env:
          PRODCHECK_SITE: https://prodcheck.pages.dev
        run: python3 scripts/build_site.py
```

## About js.org

`prodcheck.js.org` was [requested and declined](https://github.com/js-org/js.org/pull/12407).
The maintainer's reasoning was correct and worth recording: JS.ORG requires the *content*
to be specific to JavaScript developers, and 92% of this checklist is deliberately
stack-agnostic. Only 324 of 4,124 items are Node or JavaScript specific, and the homepage
example is Django.

That is a property of the project, not a mistake to correct. Changing the example to
Next.js would have gamed the review rather than answered it.

If a short domain matters, buy one — the switch is one environment variable.

## What the site serves

| | |
| --- | --- |
| `sitemap.xml`, `robots.txt` | submitted and crawlable |
| `llms.txt` | for answer engines |
| `_headers` | CSP, `X-Content-Type-Options`, `Referrer-Policy`, frame denial, cache lifetimes — read by Cloudflare Pages, ignored by GitHub Pages |
| `og.png` | 1200×630, generated from the live counts by `scripts/build_og.sh` |

GitHub Pages cannot set response headers, which is one honest reason to prefer Cloudflare
for the primary host: the security headers in `_headers` only take effect there.
